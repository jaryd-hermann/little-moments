# Expo iOS boilerplate — master prompt and technical spec

Use this document as a **single artifact**: host it, sell it, or paste the [Master prompt (copy-paste)](#master-prompt-copy-paste) section into Cursor (or another coding agent) to scaffold a **new** app. It is designed so the first **EAS iOS** build is boring, not a dependency whack-a-mole.

**Selling point:** “Works out of the box” means a **physical iPhone** install from an **EAS binary** (not simulator-only). Simulator success is **dev convenience**, not the product bar — see [Device-first verification](#device-first-verification-not-simulator-only).

---

## What this delivers

- **Expo SDK–pinned** stack (one compatibility spine: Node → Expo → React → React Native → TypeScript).
- **expo-router** file layout: splash, auth, onboarding, **four** bottom tabs, home when logged in, **settings** as a modal.
- **NativeWind v4** + Metro + Babel rules that agents commonly break.
- **Backend**: **Supabase** with **email + password** (register and sign-in); **`public.profiles`** schema + RLS + trigger + backfill SQL included below.
- **Analytics**: **PostHog** (`posthog-react-native`) — **lazy / deferred** until after auth hydration; **no init** if the API key is missing or still a placeholder (avoids early native crashes on device — see [Cold start: PostHog and optional native SDKs](#cold-start-posthog-and-optional-native-sdks)).
- **Monetization**: **RevenueCat is not part of the default boilerplate.** Add it only **after** a device `preview` / internal build runs clean (see [RevenueCat (add-on after device build)](#revenuecat-add-on-after-device-build)).
- **New Architecture**: **`newArchEnabled: true`** in `app.config.ts` — **required** for **react-native-reanimated ~4.x** on iOS (`RNReanimated.podspec` asserts New Arch; `pod install` fails if it is off). Aligns with production apps such as Little Moments — see [New Architecture (required)](#new-architecture-required).
- **EAS**: profiles, env discipline, **no dev-client binaries on store/TestFlight paths**, **remote developer build numbers** with **auto-increment**, and a documented **submit** flow — see [EAS profile discipline](#eas-profile-discipline-store-vs-dev-client).
- **Splash / auth bootstrap**: documented pattern so **`hydrated` never deadlocks** the native splash (see [Native splash, in-app splash, and hydration](#native-splash-in-app-splash-and-hydration-no-deadlock)).

## Human preflight — do this before `npm install` / first run

The agent **must** pause after scaffolding and give the human these steps **in order**, before walking through local install (`npm install`, `npx expo start`, etc.):

1. **Supabase** — In the project root, create `.env` from `.env.example` and paste:
   - `EXPO_PUBLIC_SUPABASE_URL`
   - `EXPO_PUBLIC_SUPABASE_ANON_KEY`

2. **PostHog** — Paste a real `EXPO_PUBLIC_POSTHOG_API_KEY` into `.env`. If the value is still the `.env.example` placeholder, the app must **skip** PostHog native init until a valid key is set ([Cold start: PostHog and optional native SDKs](#cold-start-posthog-and-optional-native-sdks)).

3. **EAS environment sync (required for device/TestFlight builds)** — After the human says “keys added,” the agent must write these same keys into EAS env for **`development`**, **`preview`**, and **`production`**:
   - `EXPO_PUBLIC_SUPABASE_URL`
   - `EXPO_PUBLIC_SUPABASE_ANON_KEY`
   - `EXPO_PUBLIC_POSTHOG_API_KEY`

   Verify with:
   - `eas env:list --environment development`
   - `eas env:list --environment preview`
   - `eas env:list --environment production`

   If any key is missing, do not continue to device build steps.

4. **Database** — In the Supabase dashboard: **SQL Editor** → run the full script from [Profiles SQL (required migration)](#profiles-sql-required-migration). In this repo the same script lives at [`docs/sql/boilerplate-0001-profiles.sql`](sql/boilerplate-0001-profiles.sql) for copy-paste; greenfield apps generated by the prompt should also commit it as `supabase/migrations/0001_profiles.sql` (or the next free migration number). Confirm success before expecting sign-up to work with `profiles`.

Only after (1)–(4) should the README continue with Node version check, `npm install`, `npx expo-doctor`, and `npx expo start`.

## Native splash, in-app splash, and hydration (no deadlock)

### What the user sees

| Screen | What it is |
|--------|------------|
| **Default Expo native splash** | Image from `app.config.ts` / `expo-splash-screen` plugin (e.g. `assets/images/splash-icon.png`) — the template grid/circles. **Not** your `app/splash.tsx` route. |
| **In-app splash** | Your route `app/splash.tsx` (e.g. “Test App” + button) — only after JS loads and the router mounts. |

A **few seconds** on the native splash while Metro loads, fonts load, and auth hydrates is **normal**. **Stuck forever** on the native splash is a **hang** — almost always a logic bug, not “slow Expo.”

### Deadlock to avoid (critical)

**Anti-pattern:** `hydrated` (or equivalent) is set to `true` only inside a child component (e.g. “RootStack”) that **only mounts when `hydrated` is already true**. Then:

- `hydrated` never becomes `true` → child never mounts → `hydrated` never runs → **`SplashScreen.hideAsync()` never runs** → user stares at the native splash forever.

**Required pattern:**

- Run **auth bootstrap** in **`app/_layout.tsx` (root layout)** — or in a module that runs **before** any UI that is gated on `hydrated`:
  - Zustand `persist` rehydration (if used)
  - `supabase.auth.getSession()` (initial session)
  - `supabase.auth.onAuthStateChange` subscription
  - Set `hydrated` / `isReady` to `true` **in the same layout** after `getSession` resolves (and persist rehydrate completes if applicable)
- Only **then** render the root `Stack` (or call `SplashScreen.hideAsync()` alongside fonts if you split concerns — but **never** hide splash only inside a subtree that waits on `hydrated` that the subtree itself is supposed to set).

**Rule of thumb:** anything that flips “app is ready to show UI” must run in code that mounts **on first paint**, not inside a branch that waits for that flag.

## Device-first verification (not simulator-only)

| Bar | Requirement |
|-----|-------------|
| **Not sufficient** | “It launches in iOS Simulator with Metro.” Simulator uses different timing and often misses **Release** / **device-only** native crashes. |
| **Required before claiming “verified”** | Install on a **physical iPhone** an **EAS-built** `.ipa` (e.g. **`preview`** internal distribution or **TestFlight**), built with **`ios.simulator`: false** for that artifact. Cold-launch twice (kill app, reopen). |
| **README** | Document the exact commands: e.g. `eas build -p ios --profile preview`, install via internal link or TestFlight, minimum iOS version tested. |

Boilerplate sellers should run this matrix once per **Expo SDK version** they advertise.

## New Architecture (required)

**react-native-reanimated 4.x** ships an iOS podspec that calls **`assert_new_architecture_enabled`**. If **`newArchEnabled`** is **`false`**, Expo sets **`RCT_NEW_ARCH_ENABLED=0`** and **`pod install` fails** with the Reanimated error you saw — this is not optional for the pinned stack (**Reanimated ~4.1** + Expo SDK **54** family).

| Rule | Detail |
|------|--------|
| **Default** | In **`app.config.ts`**, set **`newArchEnabled: true`** (matches Little Moments and Expo’s supported matrix for this Reanimated line). |
| **EAS / shell** | **Do not** set **`RCT_NEW_ARCH_ENABLED=0`** in EAS env, CI env, or local shell when using this boilerplate — it brings the same pod failure back. |
| **Device crashes** | Mitigate with **deferred PostHog**, **env guards**, **no dev client on store builds**, and **device `preview` verification** — not by turning New Arch off (pods will fail). |
| **If you truly need Old Arch** | That is a **different SKU**: you would need an older **Reanimated 3.x** (and Expo/RN versions that support it), not a one-line config flip — out of scope for this “LM-aligned” boilerplate. |

Re-verify this section when upgrading Expo SDK / Reanimated major.

## Cold start: PostHog and optional native SDKs

Early **`EXC_BAD_ACCESS` / Hermes** crashes on **device** (especially **Release**) often correlate with **native analytics or purchases initializing on the first frame**, before the bridge is stable. **Do not** try to fix that by disabling New Architecture here — **Reanimated 4** requires it for iOS pods ([New Architecture (required)](#new-architecture-required)).

| Rule | Detail |
|------|--------|
| **PostHog** | Do **not** mount `PostHogProvider` (or call PostHog init) until **after** auth bootstrap has set **`hydrated` / ready** and the native splash is cleared (or immediately after `SplashScreen.hideAsync()`, same tick is OK if no native work runs before hide). Optionally wrap PostHog setup in **`InteractionManager.runAfterInteractions`** for an extra deferral. |
| **Env guard** | If `EXPO_PUBLIC_POSTHOG_API_KEY` is **undefined**, **empty**, or equals a documented **placeholder** (e.g. `your_posthog_key_here`), **skip** PostHog entirely (render children without `PostHogProvider`, or a no-op provider). **Never** pass an invalid key into native init on a Release build. |
| **Surveys** | Omit `PostHogSurveyProvider` from the default boilerplate unless required — fewer native edges on cold start. |
| **Order in `app/_layout.tsx`** | `GestureHandlerRootView` → run **`getSession` / `onAuthStateChange`** → **`hideAsync`** when ready → **then** enable PostHog subtree. Supabase client can exist early (JS-only until network); PostHog is the sensitive native touch. |

## EAS profile discipline (store vs dev client)

| Mistake | Why it hurts |
|---------|----------------|
| **Store / TestFlight binary built with `developmentClient: true`** | Wrong artifact class; confusing crashes and “dev” native behavior. |
| **Claiming production readiness from simulator-only** | Misses device Release crashes. |

| Profile | Typical use |
|---------|-------------|
| **`development`** | `developmentClient: true`, **simulator OK** for daily dev. |
| **`preview`** | **No dev client** (`developmentClient` false or omitted); **internal distribution**; **`ios.simulator: false`** when verifying “real phone” bar. |
| **`production`** | App Store / TestFlight production track; never the dev client. |

Document in README: **which profile** to use for **TestFlight vs internal vs local sim**.

## Technical spec

### Stack

| Concern | Choice |
|--------|--------|
| Framework | **Expo** (managed workflow) |
| Routing | **expo-router** (`package.json`: `"main": "expo-router/entry"`) |
| UI | **React Native** + **NativeWind v4** (Tailwind **3.4.x** — not Tailwind CSS v4) |
| Navigation primitives | `@react-navigation/native`; tabs via expo-router `Tabs` |
| Gestures / animation | `react-native-gesture-handler` (root `GestureHandlerRootView`), `react-native-reanimated` |
| Auth + API | **Supabase** (`@supabase/supabase-js`) — **email + password** (sign up + sign in); session in **AsyncStorage** |
| Analytics | **PostHog** (`posthog-react-native`) — mount **only after** auth hydration + splash cleared; **env-guarded** (see [Cold start: PostHog and optional native SDKs](#cold-start-posthog-and-optional-native-sdks)) |
| Subscriptions | **Not in default scaffold** — add **RevenueCat** only after device build passes ([RevenueCat (add-on after device build)](#revenuecat-add-on-after-device-build)) |
| New Architecture | **`newArchEnabled: true`** — **required** for Reanimated 4 iOS pods ([New Architecture (required)](#new-architecture-required)) |
| App state | **Zustand** + Supabase session; onboarding flags persisted as needed |
| Config | **`app.config.ts`** (typed), not static-only `app.json` |
| Splash | `expo-splash-screen`: `preventAutoHideAsync()` in root; **`hideAsync()`** after **fonts (if any) + auth hydration ready** — see [Native splash, in-app splash, and hydration](#native-splash-in-app-splash-and-hydration-no-deadlock) |
| TypeScript | `strict: true`, `extends: "expo/tsconfig.base"`, path alias `@/*` → repo root |

### Supabase (email + password)

| Item | Requirement |
|------|-------------|
| Client | `npx expo install @supabase/supabase-js @react-native-async-storage/async-storage` |
| Polyfill | `import "react-native-url-polyfill/auto"` **once** at entry (before creating the client) — required for React Native + Supabase |
| Client config | `createClient(url, anonKey, { auth: { storage: AsyncStorage, autoRefreshToken: true, persistSession: true, detectSessionInUrl: false } })` |
| Env | `EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_ANON_KEY` in `.env` / EAS — never commit real values |
| Dashboard | **Authentication** → enable **Email** provider; allow email + password sign-up as needed for your product |
| Sign-in screen | **Email + password only**: **Register** via `signUp({ email, password, options: { data: { full_name } } })` (optional `full_name` in metadata); **Login** via `signInWithPassword({ email, password })`. Toggle UI between register and login modes. Handle errors (weak password, user already exists, wrong password). |
| Profiles | After the SQL migration runs, each new `auth.users` row gets a `public.profiles` row via trigger; app reads/writes `profiles` for `full_name` etc. |

### PostHog (analytics)

| Item | Requirement |
|------|-------------|
| Package | `posthog-react-native` installed with a version compatible with your Expo SDK (prefer versions Expo Doctor accepts). |
| **Cold start** | Mount `PostHogProvider` **only after** auth `hydrated` is true **and** `SplashScreen.hideAsync()` has run (or same completion callback). Optionally defer with `InteractionManager.runAfterInteractions`. Do **not** wrap the entire app in PostHog at the top of the file before session hydration. |
| **Env guard** | If key is missing, empty, or placeholder string, **do not** call PostHog native init — render app without analytics until a valid key is configured. |
| Provider | When enabled: `PostHogProvider` with valid `apiKey` and `options={{ host: "https://us.i.posthog.com" }}` (or EU host). |
| Env | `EXPO_PUBLIC_POSTHOG_API_KEY` — never commit the real key. |
| Usage | Use `usePostHog()` only under provider; keep event names stable and documented in README. |

Default boilerplate: **omit** `PostHogSurveyProvider` unless you explicitly want surveys on day one.

### EAS workflow (builds and env)

1. Install CLI: `npm i -g eas-cli` or `npx eas-cli` (match `eas.json` `cli.version` if you pin one).
2. `eas login`, then `eas init` in the project.
3. **`eas.json`** profiles (minimum) — see [EAS profile discipline](#eas-profile-discipline-store-vs-dev-client):
   - **`development`**: `developmentClient: true`, iOS simulator distribution for fast iteration.
   - **`preview`**: **no dev client**; internal distribution; use **`ios.simulator: false`** for the artifact you install on a **physical iPhone** to verify the boilerplate.
   - **`production`**: store-bound; **never** `developmentClient: true`; use **remote version source** + **`autoIncrement`** (see next section).
4. All **`EXPO_PUBLIC_*`** runtime values required by the app (**at minimum** `EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_ANON_KEY`, `EXPO_PUBLIC_POSTHOG_API_KEY`) must be present in **EAS env** for each environment used in cloud builds (`development`, `preview`, `production`). **Never** set **`RCT_NEW_ARCH_ENABLED=0`** in EAS env for this boilerplate (breaks Reanimated 4 iOS pods).
5. After any native dependency: **`npx expo install <package>`**.
6. Gate before “done”: **`npx expo-doctor`** — fix all reported issues.

## Automatic build versions and submission (no manual build-number edits)

This workflow follows Expo’s [App version management](https://docs.expo.dev/build-reference/app-versions/) (remote source + auto-increment for **developer-facing** build numbers).

### Concepts (two different numbers)

| Value | Apple (iOS) | Who bumps it |
|-------|----------------|--------------|
| **User-facing** | `CFBundleShortVersionString` ← `version` in app config | **You intentionally** when starting a new App Store release (e.g. `1.0.0` → `1.1.0`). Expo recommends treating this as the start of a release cycle. |
| **Developer-facing** | `CFBundleVersion` ← `ios.buildNumber` | **EAS (remote)** when `appVersionSource` is `remote` and `production.autoIncrement` is `true` — **no manual per-build edits**. |

Android mirrors this: `version` / `versionName` vs `android.versionCode`.

### Places to configure (checklist)

1. **`eas.json` → `cli.appVersionSource`**  
   Set to **`"remote"`**.  
   EAS stores **iOS `buildNumber`** and **Android `versionCode`** on Expo servers; those values override whatever is in native output at **build** time (values in `app.config.ts` for build numbers are **not** the source of truth once remote is active — you can omit `ios.buildNumber` / `android.versionCode` from config after migration, per Expo).

2. **`eas.json` → `build.production` → `autoIncrement`**  
   Set to **`true`**.  
   Each **`eas build -p ios --profile production`** (and Android production builds) increments the **remote** developer build version so App Store Connect / Play Console do not reject duplicates.

3. **`eas.json` → `build.development` and `build.preview`**  
   Typically **omit** `autoIncrement` (or leave false) so internal builds do not consume production build-number sequences. Use simulator / internal distribution as needed.

4. **`app.config.ts` → `version`**  
   Keep this as the **marketing** semver you want in the store for the **current release train**. Bump it when you ship a **new** version to users (e.g. after `1.0.0` is live, set `1.1.0` before the next store submission). This is **not** auto-incremented by EAS in the remote-build-number workflow.

5. **First-time or migrating apps**  
   If the app already exists in the stores, run **`eas build:version:set`** (see Expo doc above), choose platform, confirm remote, and initialize with the **last shipped** build number / version code so EAS continues from the correct sequence.

6. **Syncing local Xcode/Gradle with remote (optional)**  
   **`eas build:version:sync`** pulls remote build versions into the local project for local opens in Xcode/Android Studio.

7. **Submission without Transporter drudgery**  
   - Build: `eas build -p ios --profile production`  
   - Submit latest production iOS artifact:  
     `eas submit -p ios --profile production --latest`  
   Configure **`submit.production.ios`** in `eas.json` (e.g. `appleId`, and `ascAppId` if required) so non-interactive CI can submit. Apple credentials are managed via **EAS credentials** (`eas credentials`), not pasted into the repo.

### What you do **not** do

- Do not bump `ios.buildNumber` in `app.config.ts` before every CI build when using **remote** + **`autoIncrement`** for production.
- Do not rely on manually uploading in App Store Connect to “fix” version codes for routine releases; let EAS increment the developer-facing value.

### Optional: CI one-liner pattern

```bash
eas build -p ios --profile production --non-interactive
eas submit -p ios --profile production --latest --non-interactive
```

Bump `version` in `app.config.ts` only when you intentionally cut a **new marketing release**.

### Limitations (Expo)

- If you use **EAS Update** with `runtimeVersion` policy `"nativeVersion"`, remote versioning has constraints; Expo recommends **`appVersion`** policy for similar behavior. See [Expo app versions](https://docs.expo.dev/build-reference/app-versions/#limitations).

### “Done” definition

- `npx expo start` runs without Metro red errors.
- `npx expo-doctor` passes (or documented waivers only).
- **`app.config.ts`** sets **`newArchEnabled: true`** (required for Reanimated ~4.1 iOS); README documents **not** setting `RCT_NEW_ARCH_ENABLED=0` in EAS.
- Native splash **clears** after load (no `hydrated` deadlock); PostHog mounts **only after** hydration + env guard satisfied.
- Email + password register and sign-in work; `profiles` row exists after sign-up.
- PostHog receives at least one test event **after** deferred init (sim or device).
- **`eas build -p ios --profile development`** succeeds when credentials exist (simulator OK for dev loop).
- **`eas build -p ios --profile preview`** with **`ios.simulator: false`** installs on a **physical iPhone** and cold-launches **twice** without crash (this is the **sellable** “works out of the box” bar — see [Device-first verification](#device-first-verification-not-simulator-only)).
- Default scaffold **excludes** RevenueCat until the add-on step is followed.
- Production path: **`remote`** + **`autoIncrement`** documented; team knows when to bump **`version`** vs relying on EAS for build numbers.

## Profiles SQL (required migration)

Ship in the repo as **`supabase/migrations/0001_profiles.sql`** on greenfield projects (or the next migration index your tool expects). Canonical copy in Little Moments: [`docs/sql/boilerplate-0001-profiles.sql`](sql/boilerplate-0001-profiles.sql). Run in the Supabase **SQL Editor** during [Human preflight](#human-preflight--do-this-before-npm-install--first-run).

This migration:

- Creates **`public.profiles`** — `id` (PK, FK → `auth.users`), `email`, `full_name`, `created_at`, `updated_at`
- Adds **`updated_at`** trigger on row update
- Enables **RLS** — authenticated users can **SELECT / INSERT / UPDATE** only their own row (`auth.uid() = id`)
- Adds **`handle_new_user()`** — `SECURITY DEFINER` trigger on **`auth.users` AFTER INSERT** → inserts matching `profiles` row (`ON CONFLICT DO NOTHING` for safety)
- **Backfill** — inserts profiles for users already in `auth.users` but not in `profiles` (`ON CONFLICT DO NOTHING`, safe to re-run)

```sql
-- public.profiles: one row per auth user
CREATE TABLE IF NOT EXISTS public.profiles (
  id UUID PRIMARY KEY REFERENCES auth.users (id) ON DELETE CASCADE,
  email TEXT,
  full_name TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- updated_at on any UPDATE
CREATE OR REPLACE FUNCTION public.handle_profiles_updated_at()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
  NEW.updated_at = NOW();
  RETURN NEW;
END;
$$;

DROP TRIGGER IF EXISTS profiles_set_updated_at ON public.profiles;
CREATE TRIGGER profiles_set_updated_at
  BEFORE UPDATE ON public.profiles
  FOR EACH ROW
  EXECUTE FUNCTION public.handle_profiles_updated_at();

ALTER TABLE public.profiles ENABLE ROW LEVEL SECURITY;

DROP POLICY IF EXISTS "profiles_select_own" ON public.profiles;
DROP POLICY IF EXISTS "profiles_insert_own" ON public.profiles;
DROP POLICY IF EXISTS "profiles_update_own" ON public.profiles;

CREATE POLICY "profiles_select_own"
  ON public.profiles FOR SELECT
  TO authenticated
  USING (auth.uid() = id);

CREATE POLICY "profiles_insert_own"
  ON public.profiles FOR INSERT
  TO authenticated
  WITH CHECK (auth.uid() = id);

CREATE POLICY "profiles_update_own"
  ON public.profiles FOR UPDATE
  TO authenticated
  USING (auth.uid() = id)
  WITH CHECK (auth.uid() = id);

-- New auth.users row -> public.profiles row (runs with definer rights; bypasses RLS for insert)
CREATE OR REPLACE FUNCTION public.handle_new_user()
RETURNS TRIGGER
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public
AS $$
BEGIN
  INSERT INTO public.profiles (id, email, full_name)
  VALUES (
    NEW.id,
    NEW.email,
    COALESCE(NEW.raw_user_meta_data->>'full_name', '')
  )
  ON CONFLICT (id) DO NOTHING;
  RETURN NEW;
END;
$$;

DROP TRIGGER IF EXISTS on_auth_user_created ON auth.users;
CREATE TRIGGER on_auth_user_created
  AFTER INSERT ON auth.users
  FOR EACH ROW
  EXECUTE FUNCTION public.handle_new_user();

-- Backfill existing auth users (idempotent)
INSERT INTO public.profiles (id, email, full_name)
SELECT
  u.id,
  u.email,
  COALESCE(u.raw_user_meta_data->>'full_name', '')
FROM auth.users AS u
LEFT JOIN public.profiles AS p ON p.id = u.id
WHERE p.id IS NULL
ON CONFLICT (id) DO NOTHING;
```

If your Supabase Postgres build rejects `EXECUTE FUNCTION`, use `EXECUTE PROCEDURE` instead for the two triggers (both spellings are common across Postgres versions).
